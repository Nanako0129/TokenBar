# 量測與對拍

## 文件目的

Syrtis 的效能與正確性主張大多是**經驗性**的：某個改動更快、某個改動不改變輸出。這類主張很容易在看起來完全正常的情況下失效，而失效方式是可以列舉的。

這份文件記錄那些方式，以及對應的協定。它來自 2026-08 那輪載入延遲調查——那輪的 oracle 換了五個版本、每一版都通過了當時的檢查、前四版事後都證明是瞎的。實測數字與結論在 [`history/dashboard-load-performance.md`](history/dashboard-load-performance.md)。

> 建立語料的可執行腳本不在本文範圍。那需要複製帶憑證的真實目錄、判斷 symlink 是否通往活資料、以及破壞性清理，是機器相關且安全敏感的工作，屬於操作者的私有覆蓋層。本文記的是**協定**：要成立什麼條件，量測才算數。

## 三個角色不要混在同一份文件

一份文件可以是**歷史紀錄**、**未來的量測規範**、或**某個變更的驗收證據**。三者混在一起會產生一個看不見的成本：

> 協定只要改嚴一條，舊數據的有效性、統計方法、表格標題、摘要數字與出貨結論就**全部**要一起重算。

而驗收角色還帶另一個問題：**經驗性有效性主張的合格質疑供給是無限的。** 任何一個「你有沒有控制 X」都可以是真的——估計量、語料身分、binary 身分、arm 順序、熱殘留、硬體前提。所以一份自我宣告「協定合格」的歷史文件，審查永遠不會結束。

實務結論：

- 歷史文件記**量到什麼、什麼被推翻、限制是什麼**，明寫它不是驗收證據
- 驗收證據在**做那個變更的 PR** 裡產生，按當下的協定量
- 協定（本文）獨立維護，改它不需要重算任何歷史數字

## 對拍 oracle

對拍 oracle 需要**兩個**性質，而且要分開證明：

| 性質 | 意思 | 怎麼證 |
|---|---|---|
| **穩定** | 同一份輸入跑兩次給同一個結果 | 零改動對拍：`OLD-a == OLD-b` |
| **敏感** | 輸出真的變了結果就要變，**沒真的變就不能變** | 正負兩面的變異：該變的要變、不該變的不能變 |

**只證穩定是不夠的，而且不夠的方式很致命：一個永遠回傳常數的 oracle 會通過所有的相等檢查。** 本專案的 digest 前四版全部通過了零改動對拍，全部是瞎的。

### 敏感度不能靠讀程式碼回答

前四版每一版都附了一套聽起來成立的覆蓋面論證，四版全錯。唯一可行的是變異：

1. 取一份真實輸出
2. 套用一個**已知會改變它**的變異
3. 要求 oracle 的值改變
4. **帶負對照**：一個按設計**不該**改變結果的變異（例如重排一個本來就無序的容器），要求值**不變**

沒有第 4 點，前三點全過也可能只是「這個 oracle 對什麼都敏感」。

變異記憶體裡的結果物件、而不是變異引擎，可以把問題隔離到 oracle 本身，而且一次掃描就能得到全部判定。

**本專案實際跑過的那一組**（基準 digest `6031430621329286087`，取第一個含 ≥2 個 client 列的日期）。每個變異對應一種這個 oracle **真實存在過**的盲點：

| 變異 | 期望 | 結果 | 對應的失明版本 |
|---|---|---|---|
| 某列 `provider_id` 改一個字元 | 變 | ✅ | v2（只雜湊 client／model／訊息數／成本） |
| `time_metrics.session_count` +1 | 變 | ✅ | v3（五個欄位只雜湊 `contributions`） |
| 交換兩天 `contributions` | 變 | ✅ | v4（把有序陣列一併排序） |
| 某列 `cost += 1e-9` | 變 | ✅ | 固定小數位字串化磨掉的精度 |
| **交換同一天的兩個 client 列** | **不變** | ✅ | 負對照 |

最後一列最容易被略過。沒有它，前四列全過也可能只是「這個 digest 對任何改動都敏感」，而那同樣不是一個可用的 oracle。

### 設計規則

**不要手動列舉要雜湊的欄位。** 序列化整份結果再正規化，新欄位自動進去。手動清單會在有人加欄位的那一刻無聲停止覆蓋。

**預設要選「漏掉會大聲失敗」的那一邊。** 兩種名單的錯誤方向不對稱：

| 名單 | 漏掉一項的後果 |
|---|---|
| 排除清單（volatile 鍵、無序容器） | `OLD-a != OLD-b`，當場停住 |
| 包含清單（要雜湊的欄位、要排序的容器） | 安靜地少看一塊，綠燈照亮 |

所以 volatile 鍵用排除清單；容器順序**預設保留**，只對確知無序的路徑排序。反過來做會讓 oracle 對「順序改變」失明，而那正是排序類改動最可能造成的回歸。

**排序用 JSON path 指定，不要用鍵名。** 同名的容器可能一個無序、一個有序。

**別自己磨掉精度。** 固定小數位字串化會讓小於該位數的差異隱形，那是一個程式碼從未宣告、文件從未論證過的容差。

**oracle 定義改一次，舊數值全部作廢。** 兩支 probe 都要重編、全部 arm 都要重跑，數值一律與 commit 綁定記錄。

## 計時協定

同組態的兩次冷跑在開發機上曾相差 **9.4 秒**，所以任何單次比較都不成立。

1. 每對 OLD／NEW 用**同一份不可變語料**與同一組環境
2. 每個 arm 從等價的空快取狀態開始
3. 一個 arm 是**兩次執行**：清快取後跑一次（冷），再對它剛寫出來的快取跑一次（暖）。冷與暖都從同一個 arm 取，否則暖啟動的數字與門檻沒有定義
4. **交錯**執行以抵銷漸進漂移
5. **區分兩種失敗。** 準備或環境失敗（清快取失敗、語料不可讀、機器被別的工作佔住）→ 整對作廢並記錄。**被測 binary 自己的執行失敗（崩潰、逾時、被殺）→ 驗收失敗**，不是作廢：把失敗的對丟掉、只留成功的執行，等於讓一個間歇崩潰的實作通過驗收，而那正是可靠性證據本身。要容許少量失敗就必須**事前宣告**上限並把**所有嘗試**列進報告
6. **任何作廢都必須「看不到結果也能判定」。** 這條管的是所有作廢理由，不只上面那一種——每開一個裁量的出口，就等於開一條「看到不喜歡的數字再宣告它不算」的路，而在最差對規則下丟掉一個慢的 NEW 就足以翻轉結論。所以：作廢條件要**事前宣告**，且必須依賴**與量測結果無關**的可觀察訊號（取樣期間的系統負載、溫度、有沒有其他程序在跑），不能是「這次特別慢，應該是機器忙」；**每一次作廢都要連同當時觀察到的訊號列進報告**，作廢次數本身是資料；判不出來就不要作廢，讓它留在集合裡
7. 清快取本身會失敗（`Directory not empty`）。那是 **arm 準備失敗**，不是比較髒的樣本——它違反第 2 點，而配對抵銷不了不對稱的快取命中。整對作廢
8. 統計量要**成對算**：每一對算一個差值再彙總。分別取 NEW 與 OLD 的中位數不是配對估計量，兩個中位數可能來自不同對，配對就白做了
9. 記錄語料識別、**binary SHA**、環境與熱狀態

### 判定規則

同組態的兩次冷跑差過 9.4 秒，所以「跑幾對、看哪個統計量、界限多少」都不能臨場決定——否則同一組資料可以支持通過也可以支持不通過。

- **界限要在取樣之前宣告**，寫在該次變更的 PR 描述或 plan 裡。本專案引擎變更目前用的預設是：冷啟動 ≥20% 改善、暖啟動 ≤+5% 退化、峰值 RSS ≤+25% 退化。換一種變更就換一組界限，但**先宣告再量**這件事不變
- **最少 4 對**，且**兩種順序的對數必須相等**（`OLD→NEW` 與 `NEW→OLD` 各半）。只要求偶數不夠：四對全是 `OLD→NEW` 也滿足偶數與交錯，卻沒有任何 `NEW→OLD` 區塊可比，順序相關的熱殘留就整個藏起來。順序序列同樣要事前宣告（交錯或隨機皆可，宣告了就照做）
- **界限套在最差的那一對，不是中位數**
- 中位數與最差對**都要寫進報告**，只報一個等於讓讀者無法判斷落在哪種情況

**最差對沒過時，唯一的補救是整組重跑。** 不能加對——最差對是保留集合的極值，加樣本只會讓它不變或更差，「加對直到過」實際上等於慫恿把壞的那對丟掉。所以：修正原因（通常是 washout 不足）之後**整組重來**，舊的那組作廢並照實記錄它存在過。

這條規則刻意比「看中位數」嚴。它的好處是**確定性**：不需要顯著性檢定，也不會因為事後選了哪個統計量或哪個界限而改變結論。

### 配對抵銷不了熱殘留

兩個 arm 的發熱量不同時（較慢的那個跑得久、發熱多），下一個 arm 繼承的熱狀態**取決於前一個 arm 是誰**。`OLD→NEW` 會拖慢 NEW，`NEW→OLD` 的殘留方向相反。**這是與處理相關的偏差，不是配對能吸收的隨機漂移**，而且奇數對會讓兩種順序不平衡。

**分順序區塊只是呈現，不是控制。** 偶數對讓兩種順序數量相等，但每個區塊內的第二個 arm 仍然繼承與處理相關的熱，所以兩個區塊的估計值都還是有偏的——只是偏的方向被分開看見而已。

真正的控制是 **washout**：每個 arm 之前回到等價的熱基準（固定冷卻時間，或量到溫度／頻率回到基線）。分區塊呈現保留下來當**診斷**用——兩個區塊差很多就代表 washout 不足，該延長冷卻而不是取中位數蓋過去。

熱節流的量級：連續跑 12 次 40 秒的冷掃描之後，中位數比機器閒置時單跑高約 **6.3 秒**（40,944ms vs 34,596ms）。

## 正確性協定

**每一個 arm 之前都要重建乾淨快取，`NEW` 之前也一樣**——這是最容易漏掉的一次：

1. 用不可變、已清理的語料
2. 重建乾淨快取 → 執行 `OLD-a`
3. 重建乾淨快取 → 執行 `OLD-b`
4. **`OLD-a != OLD-b` 就停**——oracle 尚未穩定，這時要修的是 oracle，不是宣布通過
5. 重建乾淨快取 → 執行 `NEW-a`
6. 重建乾淨快取 → 執行 `NEW-b`
7. **`NEW-a`、`NEW-b` 都必須等於基準**
8. **冷與暖的輸出都要對拍。** 每個 arm 在冷執行之後、對它剛寫出的快取再跑一次，比較那一次的 digest。只比冷的等於只比 miss 路徑——而快取命中重播是獨立的一段程式（批次化就改了 exact-hit 的處理方式），只出現在暖執行裡的回歸會完整通過一份只有冷對拍的驗收
9. **證明 oracle 敏感，正負兩面都要。** 一個**已知會改變輸出**的變異必須讓數值改變，而一個**按設計不該改變結果**的變異（重排一個本來就無序的容器）必須讓數值不變。只做正面那一半，一個錯誤地把無序容器納入雜湊的 oracle 可以通過上面每一步——只要那次的走訪順序碰巧穩定——然後在真正等價的另一種順序上謊報回歸

漏掉第 5 步的重建，`NEW` 會重播 `OLD-b` 寫進去的條目，而不是走它自己的 miss 路徑——**那正是要驗的東西**。結果仍然會相等，只是相等的原因變成「兩邊讀的是同一份快取」。

**`NEW` 要跑兩次，但它證明的東西比你想的小。** `OLD-a`／`OLD-b` 證明 **oracle** 穩定；`NEW-a`／`NEW-b` 是被測實作的 sanity check。**兩個 arm 必須是同一個 revision**；換一個含後續修正的 commit 不算第二個樣本，那量到的是另一個實作。

**但兩個樣本不是排程穩定性的證明。** 罕見的競爭條件連續兩次給出相同輸出毫不困難——多取一個樣本只是把僥倖機率降低，沒有改變種類。**依排程而變的回歸要由確定性的 fixture 承擔**：

| 要證明的事 | 由誰證明 |
|---|---|
| 順序／dedup 在批次邊界上的行為 | 引擎裡的確定性測試（例如跨批次邊界的 first-occurrence 斷言、hit／append／stale／uncacheable 矩陣），**且必須拿變異證明它們會紅** |
| 真實資料上的輸出等價 | digest 對拍 |
| oracle 自己可信 | 零改動對拍 ＋ 敏感度變異 |

三件不同的工作，不要讓其中一件替另一件背書。benchmark 跑在一份靜態語料上，本來就無法製造它要偵測的那種排程分歧。

「這些數值必須相同」要**寫成比較**。每個 arm 的結束狀態是那支 binary 的，不是「數值相等」；把 arm 用 `&&` 串起來，全部正常結束但吐出不同數值時仍然整串成功。

## 峰值 RSS 協定

記憶體與計時共用同一組 arm，但它的失敗方式不同：**RSS 不是連續量，它是整段執行的最大值**，所以單次尖峰就決定結果，取樣密度與快取狀態都會改變它。

1. 與計時**同一次執行**取得，不要另外跑一組——不同組執行的 RSS 不可比
2. 在**冷**那一次取（暖執行保留量小得多，會低估）
3. 用 `/usr/bin/time -l` 的 `maximum resident set size`，不要自行輪詢取樣（輪詢會漏掉尖峰）
4. 與計時同樣**成對算**：每一對算一個差值再彙總
5. 回報**配對中位數與最差的一對**。RSS 的離群值是真的，不是雜訊——最大值本來就是尾端統計

**界限：`≤ +25%` 退化，套在最差的那一對**（與計時同一條判定規則）。這個界限對應的是「批次化會提高同時保留量」這個已知的設計取捨；超過代表保留量不再被 miss 數量限制住，要回去看 hit 有沒有在平行階段被 clone。

> 「在門檻內」不等於「沒有上升」。設計論證只保證增量**有界**，從來不是零；報告要寫實際的百分比，不要寫「沒有影響」。

## 語料前提

量測前必須先有一份**已清理、不可變**的語料，以及一個與正式資料隔離的設定目錄。兩者都要：

- 已移除所有 provider 憑證
- 不是正式路徑，也不會成為刪除或寫入的目標
- 不會透過 symlink 或其他方式讀到仍在變動的外部資料

不變性的範圍是**語料與掃描器輸入**，不是整個設定目錄——`TOKSCALE_CONFIG_DIR` 底下的 message cache 是唯一允許變動的部分，而且變動方式是規定的：每個 arm 之前重建成同一個空狀態。

環境變數的語意決定語料要準備成什麼樣子：

| 變數 | 為什麼 |
|---|---|
| `HOME` | scanner roots 的來源 |
| `TOKSCALE_CONFIG_DIR` | 同時控制**快取根目錄**與 `PathRoot::Config` 的 scanner roots |
| `TOKSCALE_PRICING_CACHE_ONLY` | 避免網路抓取污染計時 |
| `RAYON_NUM_THREADS` | 對齊出貨的 `RAYON_INIT` 上限；不設會量到不會出貨的組態 |

因為 `TOKSCALE_CONFIG_DIR` 同時提供 scanner roots，**一個空目錄不是 production-equivalent 語料**。

**不要只準備掃描器兩個公開 root 的語料。** 實測過：只複製 `.claude/projects` 與 `.codex/sessions`，訊息數從 171,984 掉到 171,983、digest 隨之改變。掃描器讀的東西比那兩個 root 定義多，差一則訊息就足以讓對拍失去意義。

## 常見的自我欺騙

以下每一條都在本專案發生過，而且發生時看起來都很正常。

**綠燈只證明「沒失敗」，不證明「能失敗」。** 加測試的速度容易快過驗證測試能失敗的速度。任何非平凡的斷言都要拿變異證明它會紅。

**驗證步驟若與被驗證的動作共用假設，它只會一直同意。** 本專案有四次同一形狀：刪除與「刪完重掃」共用同一個 predicate，於是兩邊一起失明並回報成功。**驗證要用不同的鏡片看。**

**「現在無害」不等於「量測期間無害」。** 一次性讀到的活狀態不能授權一個必須橫跨整組執行才成立的決定。

**描述一個步驟不等於執行它。** 一段寫著「這裡會剝除憑證」的散文，讀起來跟真的做了一模一樣。

**修正引入的新機制本身是新程式碼。** 為了關掉一個 finding 而加的東西需要跟原問題一樣多的審查。

**保護「每一條離開路徑」，不是列舉想得到的訊號。** 列舉法失敗過兩次。

**一個契約敘述在 N 個地方，讀完 N 個才算調和。** 修個案不修類別，下一輪必然抓到殘留。改完任何一個實質語意，全文搜尋所有重複說法。

**上位的概括句會蓋過下面被限定的那一列，而讀者讀的是概括句。** 「不要重跑」寫在表格上方，就會壓掉某一列剛剛才要求的重量。

**方向對不代表數字對。** 本專案有四個先後發表的效能數字都落在 −26% 到 −28%、方向從來沒錯，但四個都不是合格結果；合格重跑給出更大的值。**瑕疵往哪個方向偏要重量才知道，不能推論。**

**離散判決比散文摘要可信。** digest 相等、測試轉紅、profile 佔比——這類有明確判決的東西不容易錯。「所以這代表 X」「這證明了 Y」才是出錯的地方。判斷一句話該不該信：**問它背後有沒有一個會失敗的檢查。**
