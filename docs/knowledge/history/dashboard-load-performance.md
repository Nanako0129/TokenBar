# Dashboard load performance

## 文件目的

保留 2026-08 那輪載入延遲調查的**結論、被推翻的假設、實測數字與量測原則**，讓後續的效能工作不必重跑已經有答案的實驗。

被推翻的假設與成立的結論同樣重要，所以一併保留。多數在這裡花掉的時間不是花在修正上，是花在**證明某條路不值得走**。

**本文不提供可直接照抄的操作腳本。** 量測需要處理真實的憑證、整份 home 目錄與破壞性清理，那是機器相關且安全敏感的工作，屬於操作者自己的私有覆蓋層（`.agent-local/`），不屬於公開的歷史文件。這裡記的是**協定與前提**：要成立什麼條件，量測才算數。

---

## 症狀與它實際上是什麼

| 回報 | 實際 |
|---|---|
| 第一層 loading 很慢（新機、Pro 機型也是） | 三份報表同時發出，互相爭用 |
| turns 要等 20 分鐘以上 | Daily／Monthly 為了 turns 另外發一次 hourly 全量掃描 |
| 重開沒有變快，感覺沒吃到快取 | 快取有效，但 process 重啟會丟掉記憶體內的快照 |

第三點最容易誤判。磁碟快取是有效的——暖啟動引擎只要約 2 秒。慢的是**那 2–5 秒完全空白**，而不是資料要重算。

## 被推翻的假設

以下每一條都量過，**都不是原因**。不要重跑。

| 假設 | 實測 | 結論 |
|---|---|---|
| rayon 執行緒上限（2）綁住冷掃描 | 2 條 28,772ms／10 條 28,078ms／6 條 31,213ms；同為 2 條的兩次相差 9.4 秒 | **差 2.4%，在雜訊內**。工作根本沒被分派出去，提高上限沒有意義——**僅對批次化之前的引擎（`5546bd5`）成立**。批次化把每檔工作真的派出去了，pin 推進之後這條要重量，不能沿用 |
| I/O 綁住 | 冷剖析顯示 86.2% 落在兩個解析 lane（CPU），工作執行緒整段閒置 | **由剖析推翻，不是由吞吐量推翻**。旁證：循序讀完 6.10 GB 單執行緒 7.6 秒（約 800 MB/s），但那不是上界——實際掃描另外還有數千次 open、metadata、取樣 read 與解析 read，吞吐量測試一個都沒模擬到 |
| 一開始就要全部年份，顆粒度太大 | 全部年份 28,734／29,526ms；只要 2026 年 28,127／34,522ms | **完全不省**。沒有日期索引，解析器必須讀完每則訊息才知道日期；年份只縮小折疊範圍 |
| 語料只多了約 1000 筆 turns，不該慢 13 秒 | turns +669，但新增位元組**約 960 MB**（codex 792 MB、claude 168 MB），佔 8.2 GB 語料的 +12% | **turns 是錯的量尺**。turns 是「一輪對話的起點」，不是位元組 |
| 快取的 bincode 序列化＋fsync 是那段序列化成本 | 剖析中連前幾名都排不上；fold、快取寫入與其餘 20 個 client 合計 13.8% | 錯。真正的成本在兩個解析 lane |
| 暖啟動可以靠先比 size+mtime 再算取樣雜湊來省 | `message_cache.rs` 早就先比 size 與 mtime 才算 | **守衛已存在**。那段 read 花在「已比對通過」的檔案上，是刻意的二次確認 |

## 剖析結果

macOS 內建 `sample`，不需要改任何程式碼，也不需要上游變更：

```
sample <pid> 25 1 -file <輸出路徑>
```

### 冷掃描（主執行緒約 20,409 個取樣 ≈ 整段掃描）

| 佔比 | 內容 |
|---|---|
| 43.2% | claude lane — `parse_claude_file_with_home` |
| 43.0% | codex lane — `parse_full_codex_raw_source` |
| — 其中 20.9% | `sha2::compress256`（快取指紋） |
| 13.8% | 其他全部（fold、快取寫入、其餘約 20 個 client） |

**兩個 lane 依序跑在主執行緒上，rayon 工作執行緒整段停在 `WorkerThread::wait_until`。** 這一次解釋了先前所有矛盾：不是 I/O、不是平行 CPU，是序列化。

### 暖掃描

| 佔比 | 內容 |
|---|---|
| ~24% | `compute_sample_hashes` 底下的 `read` syscall |

路徑是 `SourceFingerprint::check_*` → `primary_fingerprint_matches` → `compute_sample_hashes`。暖啟動的成本是**對約 8,362 個檔案逐一 `open` + `read` 取樣位元組**，不是雜湊也不是解析。

分析 `sample` 輸出時先看每個 thread 的總量：工作執行緒若整段停在 `rayon_core::WorkerThread::wait_until`，代表工作沒有被分派，這時要看的是主執行緒的自身時間。

取樣時機有兩個坑。暖階段只有 2–5 秒抓不到足夠取樣，要把暖階段重複多次拉長窗口；而父程序常把子程序輸出緩衝到最後才印，所以**不能**靠 log 出現與否判斷階段已開始，要改用「偵測到子程序後等固定秒數再取樣」。

## 量測協定

### 前提（由操作者自行準備）

量測開始前必須先有兩個根目錄：一份**已清理的語料**，一份**與正式資料隔離的設定目錄**。兩者都必須：

- 已移除所有 provider 憑證
- 不是正式路徑，也不會成為刪除或寫入的目標
- 不會透過 symlink 或其他方式讀到仍在變動的外部資料
- 在所有 correctness arm 之間保持不變

**怎麼建立這兩個根目錄不在本文範圍。** 那需要複製帶憑證的真實目錄、判斷 symlink 是否通往活資料、以及破壞性清理，是機器相關且安全敏感的工作。若要做成可執行的工具，應另立正式、可測試的 harness，而且該工具應該**接受一份已備妥的不可變語料**，而不是自己去複製整份 home 再嘗試清乾淨。

兩個環境變數的語意值得記下來，因為它們決定了語料要準備成什麼樣子：

| 變數 | 為什麼 |
|---|---|
| `HOME` | scanner roots 的來源 |
| `TOKSCALE_CONFIG_DIR` | 同時控制**快取根目錄**與 `PathRoot::Config` 的 scanner roots |
| `TOKSCALE_PRICING_CACHE_ONLY` | 避免網路抓取污染計時 |
| `RAYON_NUM_THREADS` | 對齊出貨的 `RAYON_INIT` 上限；不設會量到不會出貨的組態 |

因為 `TOKSCALE_CONFIG_DIR` 同時提供 scanner roots，**一個空目錄不是 production-equivalent 語料**。

實測過一條看似更安全的捷徑並否決：只準備掃描器兩個公開 root（`.claude/projects`、`.codex/sessions`）的語料，訊息數從 171,984 掉到 171,983，digest 隨之改變。**掃描器實際讀的東西比那兩個 root 定義多**，差一則訊息就足以讓對拍失去意義。

### 計時協定

同組態的兩次冷跑在這台機器上曾相差 **9.4 秒**，所以任何單次比較都不成立。

1. 每對 OLD／NEW 用**同一份不可變語料**與同一組環境。計時同樣需要凍結：本專案的活動會往 session log 追加寫入，而本文自己認定**位元組**才是工作量的量尺，所以一對之內的不對稱追加會直接進到量到的差值裡。交錯只能抵銷漸進漂移，抵銷不了這個
2. 每個 arm 從等價的空 message-cache 狀態開始
3. 一個 arm 是**兩次執行**：清快取後跑一次（冷），再對它剛寫出來的快取跑一次（暖）。冷與暖的數字都從同一個 arm 取，否則暖啟動的中位數與 ≤5% 退化門檻沒有定義
4. **交錯**執行（NEW/OLD、OLD/NEW…）以抵銷漂移，本次每組 7 對
5. **任一 arm 失敗，整對作廢**——配對的意義就是抵銷漂移，留下落單的觀測會直接偏移比較
6. 清快取這一步本身會失敗（可能回報 `Directory not empty`，本次量測就發生過兩次）。那是**arm 準備失敗**，不是一個比較髒的樣本：它違反第 2 點的等價空快取前提，而配對抵銷不了不對稱的快取命中。**整對作廢**，失敗要記錄下來但不進計算
7. 記錄語料識別、binary SHA、環境與熱狀態；語料識別在整組之間改變即作廢

熱節流會偽造結論：連續跑 12 次 40 秒的冷掃描之後，中位數比機器閒置時單跑高約 **6.3 秒**（40,944ms vs 34,596ms）。批次量測要把這件事算進去，或用配對比較讓它抵銷。

### 正確性協定

**計時與 digest 都需要不可變語料**，只是失效方式不同：digest 一漂移就直接失去對照意義，計時則是把語料成長混進差值裡。本專案的開發過程本身在寫 log，所以兩者都必須跑在不可變的副本上。

1. 用不可變、已清理的語料
2. 執行 `OLD-a`
3. 重建同樣的乾淨快取狀態
4. 執行 `OLD-b`
5. **`OLD-a != OLD-b` 就停**——oracle 尚未穩定，這時要修的是 digest，不是宣布通過
6. 基準穩定後才執行 `NEW`
7. `NEW` 必須與基準相同
8. 另外用一個**已知會改變輸出**的變異證明 digest 會變（見下節）

每個 arm 都要從**同一個**初始狀態開始。共用快取會讓相等變成假的：`OLD-a` 會把快取填滿，`NEW` 接著重播舊引擎寫進去的條目，而不是走它自己的 miss 解析與排序路徑——那正是要驗的東西。digest 仍然會相等，只是相等的原因變成「兩邊讀的是同一份快取」。

而「三個數值必須相同」要**寫成比較**。每個 arm 的結束狀態是那支 binary 的，不是「digest 相等」；把三個 arm 用 `&&` 串起來，三支都正常結束但吐出三個不同數值時仍然整串成功。

## digest oracle 的設計

這份規則走到第五版才收斂，前四版**每一版都在自己的 commit message 裡宣稱完整**，然後被下一輪推翻。所以規則本身不如「為什麼是這個形狀」重要。

**不要手動列舉要雜湊的欄位。** 序列化整份報表再正規化，新欄位會自動進 digest，不需要有人記得。手動清單會在有人加欄位的那一刻無聲停止覆蓋——這是 v2（漏 `provider_id` 與 token 分桶）和 v3（`GraphResult` 五個欄位只雜湊 `contributions`，漏掉獨立 fold 產出的 `time_metrics`）共同的根因。

**預設要選「會大聲失敗」的那一邊。** 兩種名單的錯誤方向不對稱：

| 名單 | 漏掉一項的後果 |
|---|---|
| 排除清單（volatile 鍵、無序陣列） | `OLD-a != OLD-b`，當場停住 |
| 包含清單（要雜湊的欄位、要排序的陣列） | 安靜地少看一塊，綠燈照亮 |

所以 volatile 鍵用排除清單，陣列順序**預設保留**、只對確知無序的路徑排序。v4 反過來做——為了修 v3 而把每個陣列都排序——結果讓 digest 對 `contributions`／`years` 的順序失明，那正是排序類改動最可能造成的回歸。修一種失明時製造了另一種。

**唯一該排序的是真正無序的容器。** 每日 client 列來自 `HashMap::into_values()`，同一個 binary 跑兩次順序就不同，v1 直接照迭代順序雜湊、零改動對拍立刻抓到。用 JSON path（`contributions[].clients`）而不是鍵名指定，否則 aggregator 已排序的 `summary.clients` 會被一起掃進去——保留它的順序反而讓 digest 對「那個排序壞掉」也保持敏感。

**別自己磨掉精度。** 固定小數位字串化會讓半微元以下的成本差異對 digest 隱形，而那是一個程式碼從未宣告、文件從未論證過的容差。用最短往返的數字表示。

**排除的只有 volatile：**`generated_at`、`processing_time_ms`。

**digest 定義每改一次，舊數值全部作廢。** 兩支 probe 都要重編、全部 arm 都要重跑，數值一律與 engine commit 綁定記錄。本文之前記過 `796241964421401448`，那是被作廢的第三版。

### 敏感度：證明 oracle 真的會失敗

**對拍全部是「相等」，而一個永遠回傳常數的 digest 會百分之百通過它們。** 相等只證明穩定，不證明敏感——這兩件事要分開證，而且敏感度**不能靠讀程式碼或逐欄位檢查覆蓋面回答**：前四版都通過了穩定性證明，也都各自附了一套聽起來成立的覆蓋面論證，四版全是瞎的。

做法是變異記憶體裡的 `GraphResult` 再算 digest（不是變異引擎），把問題隔離到 oracle 本身，一次掃描得到全部判定。每個變異對應一種**真實存在過**的盲點：

| 變異 | 期望 | 結果 | 對應的失明 |
|---|---|---|---|
| `provider_id` 改一個字元 | 變 | ✅ | v2 |
| `time_metrics.session_count +1` | 變 | ✅ | v3（只看 `contributions`） |
| 交換兩天 `contributions` | 變 | ✅ | v4（把有序陣列排序掉） |
| 某列 `cost += 1e-9` | 變 | ✅ | 固定小數位磨掉的精度 |
| **交換同一天的兩個 client 列** | **不變** | ✅ | 負對照 |

最後一項最容易被略過，但沒有它前四項也可能只是「這個 digest 對什麼都敏感」的假象。它證明每日 client 列的排序是**刻意的設計**，不是又一個沒被發現的盲點。

## 已出貨的改動

### 一、turns 折疊進 graph（PR #187）

`DailyContribution` 新增 `turns_by_client`，在 graph 的同一次掃描中依 exact client 累加 `is_turn_start`。Daily／Monthly 直接讀它，**移除第三次全量掃描**。

平行 reduction 會遺失計數，所以 `merge` 必須一併折疊該欄位——這是加欄位時最容易漏的一步。

### 二、graph 獨佔關鍵路徑（PR #187）

三份報表同時發出時，在 2 執行緒池上互相爭用，**總工作量加倍**（33 秒序列 → 67 秒並行）且延後首屏。改成 graph 先完成並 render，model 由需要它的 lens 事後請求。

| | 改動前 | 改動後 |
|---|---|---|
| 冷啟動首次繪製 | 42,953ms | **28,555ms** |
| Daily 的額外 turns 等待 | 有 | **0ms** |

真實資料驗收：94 天、12,849 turns，新舊路徑逐日逐 client 相等。

### 三、重啟還原快照（PR #192）

不同的軸——**不是縮短等待，是消除空白**。重啟後從 caches 目錄還原上一份 graph payload 立即渲染，背景刷新，右上角既有的 refresh 按鈕兼任新鮮度指示。

配額刻意不落盤（帶帳號身分），所以還原後額度卡片會短暫沒有值——那些列因此顯示「查詢中…」而不是「沒有資料」。**「沒有資料」是在宣稱問過了、沒有**，在第一次查詢落地前那是假答案。

## 尚未出貨：引擎分批平行解析（tokscale-core #6）

**這一節不在上面。** 那個 −27% 改善在 `tokscale-core` 的 main 上，TokenBar 的 `vendor/tokscale-core` pin 當時仍指向 `5546bd5`（見 `vendor/README.md`）。把它列進「已出貨」會讓人以為 TokenBar 已經含這個改善，於是跳過必要的 pin 推進與 consumer gate。要出貨到 app，得由另一個 TokenBar 變更把 reviewed gitlink 往前推。

### 設計

兩個重 lane 的每檔工作天然分成兩半：

| 階段 | 內容 | 性質 |
|---|---|---|
| A（平行） | 指紋檢查（全部檔案）＋ 解析（僅 cache miss） | 貴、每檔獨立、無共享可變狀態 |
| B（序列、原始順序） | 命中就地重播、套用快取異動、逐訊息 dedup 與 sink | 便宜、順序相依 |

關鍵限制：

- **sink 契約不變**（`S: FnMut(&UnifiedMessage)`），六個生產呼叫點一行都不用改
- **dedup 集合維持單一序列**，看到的訊息順序與改動前相同。重複鍵的訊息**內容不保證相同**，所以保序是全部的安全論證
- **命中不平行化**：exact hit 會 clone 整個快取向量，一批 32 個保留的記憶體遠超過逐檔處理。階段 A 對命中只回傳 marker
- repo 內已有此形狀的前例：materialized 相容路徑本身就是「有序平行 map ＋ 序列快取異動與 dedup」

Amdahl 上限：86.2% 理想減半、13.8% 序列，兩個 worker 的理論上限約 **1.76×**。

實測（`RAYON_NUM_THREADS=2`，隔離語料，每次清快取）。**三列來自兩組不同的執行**，這件事必須寫出來，否則整表看起來像同一組資料：

| | 資料來源 | NEW 中位數 | OLD 中位數 | 門檻 | 結果 |
|---|---|---|---|---|---|
| 冷啟動 | 7 對交錯冷跑，其中 2 對清快取失敗 | 23,587ms | 32,302ms | ≥ 20% 改善 | **−27.0%** |
| 暖啟動 | 另一組 3 對暖跑，無清快取失敗 | 1,649ms | 1,813ms | ≤ +5% 退化 | 快 9% |
| 峰值 RSS | 同上那 3 對 | 289.0 MB | 290.9 MB | ≤ +25% 退化 | 低 0.7% |

**只有冷啟動那一列受「整對作廢」影響**（下面重算）；暖與 RSS 那一組沒有 arm 失敗，沒有東西可以丟。但它有自己的弱點：**n 只有 3，而且 NEW 的第一個 arm（3,491ms）是另外兩個（1,649／1,596）的兩倍**——看起來第一次「暖」其實還沒完全暖。三對的中位數撐不起一個 ≤5% 的門檻，這兩列應該當成方向性觀察，不是驗收數據。

冷啟動的兩個區間**完全不重疊**（NEW 最大 26,117 < OLD 最小 29,769）。

**上表是「全部 arm 納入」的中位數，而那兩個中位數恰好就是兩次清快取失敗的觀測**（NEW 的 23,587 是 NEW-2、OLD 的 32,302 是 OLD-5，兩者前面都有清快取失敗）。按現在的協定這兩對整對作廢，從原始資料重算：

| 折算方式 | NEW | OLD | 差 |
|---|---|---|---|
| 全部納入（上表） | 23,587ms | 32,302ms | −27.0% |
| 只排除失敗的那兩個 arm（當時的算法） | 23,904ms | 33,090ms | −27.8% |
| **整對作廢（現行協定）** | **23,106ms** | **31,489ms** | **−26.6%** |

三種都在 −27% 上下，結論不變；**但「排除後是 −27.8%」是用一個現在已經不採用的規則算的**，不能直接當成修正值。

語料漂移：這組冷跑之間 `messages` 從 171,978 走到 171,979（+1），每個 arm 的 corpus token 不同。**但本文自己主張位元組才是工作量的量尺，而位元組差當時沒有記錄，事後也取不回來**——所以嚴格說，這組計時的污染程度在真正重要的那個維度上是未知的，只知道記錄數只多了一筆。協定已改成計時也要求不可變語料，就是為了不再需要事後這樣辯護。

RSS 沒有上升是 hit-marker 設計的直接證據：分批本身會增加保留量，但命中不 clone 就不會。

## 一條沒有被採納的路

回到上游 materialized 路徑以取回平行度——**不可行，而且不是記憶體的理由**。那條路徑的文件註解明載它不對 `simple_lane!` 的 client 做 per-client 跨檔 dedup，且解析出較窄的 client 集合，**總量會與其他報表分歧**。它是保留的 public API，不是可以直接切回去的實作。

## 方法上的教訓

| 教訓 | 來自 |
|---|---|
| oracle 必須先在零改動上證明，否則它的綠燈毫無意義 | 第一版 digest 在兩次未改動執行上就不同 |
| 穩定的 oracle 仍可能是瞎的：相等只證明穩定，敏感度要拿變異單獨證 | digest 前四版全部通過零改動對拍，全部是瞎的 |
| 變異驗證要帶負對照，否則「全部偵測到」可能只是對什麼都敏感 | 交換同一天的兩個 client 列必須**不**動 digest |
| 修一種失明時會製造另一種 | v4 為了補齊欄位涵蓋把每個陣列都排序，於是對 `contributions`／`years` 的順序失明 |
| 名單的預設方向要選「漏掉會大聲失敗」的那一邊 | 排除清單漏一項 → `OLD-a != OLD-b` 當場停住；包含清單漏一項 → 安靜少看一塊 |
| 「通過」不等於「能失敗」——加測試的速度容易快過驗證測試能失敗的速度 | 本輪兩次寫出不可能失敗的斷言，都只有靠變異跑才發現 |
| 對拍的每個 arm 都要從同一個初始狀態開始 | 共用快取時 `NEW` 會重播 `OLD-a` 寫進去的條目，相等的原因變成「讀的是同一份快取」 |
| 配對量測裡任一 arm 失敗就整對作廢 | 留下的落單觀測會偏移比較 |
| 「顯然更安全」的替代做法一樣要跑過才能採用 | 只準備兩個掃描器 root 的語料掉了一則訊息、換掉了 digest |
| 用錯的量尺會讓真實的成長看起來不合理 | turns +669 vs 位元組 +960 MB |
| 把診斷資訊丟掉會讓失敗看起來像成功 | 丟掉 stderr 讓被殺掉的程序看起來像「跑完沒輸出」；截斷輸出漏掉了最大的測試 binary |
| 跨平台 fixture 不要預測路徑拼法，去問會做查詢的那一方 | 快取 key 用 `TempDir::join` 種下，Windows 上與 scanner 的拼法不符，每個本該命中的檔案都靜默退化成重新解析 |
| 一個失敗有多種成因時，讓測試自己講是哪一種 | 「發生了 fresh parse」同時代表 key 查不到與 fingerprint 不符，分辨它們燒掉兩次 CI |
| `git diff main <branch>` 會把 **main 自己的前進**顯示成分支的刪除 | 差點據此誤報一條分支倒退了引擎 pin |
| 長時間程序要由主 session 持有 | 背景任務裡再包一層背景程序，外層一結束整個程序群被收掉 |
